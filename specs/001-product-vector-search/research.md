# Research: Product Management with Vector Search

**Branch**: `001-product-vector-search` | **Date**: 2026-05-18

## R-001: Vector Embedding in PostgreSQL Trigger vs. Python Worker

**Question**: How do we honour "trigger-driven" vector sync (Principle II) while using a heavy Python
ML model (`sentence-transformers`) that cannot run inside PostgreSQL?

**Decision**: Hybrid approach — PostgreSQL trigger + Python LISTEN/NOTIFY worker.

1. A PL/pgSQL trigger fires on `INSERT` / `UPDATE` of `products`.
2. The trigger calls `pg_notify('product_embedding_channel', product_id::text)`.
3. A long-running Python coroutine (`EmbeddingWorker`) listens on that channel via `asyncpg.Connection.add_listener`.
4. On notification, the worker loads the product, runs the embedding model, and upserts `product_embeddings`.

**Rationale**:
- The trigger fires atomically with the write — satisfying Principle II (trigger is the authoritative path).
- The heavy ML work happens in Python, avoiding PL/Python or extension dependency in PostgreSQL.
- `pg_notify` is lightweight and built-in; no external queue (Redis/RabbitMQ) needed for v1.

**Alternatives Considered**:
- **PL/Python + TensorFlow Serving**: Too complex; requires ML libraries inside PostgreSQL.
- **FastAPI BackgroundTasks**: Not trigger-driven; embedding could be skipped if handler isn't called.
- **Celery + Redis**: Correct architecture for scale, but overkill for v1.

## R-002: Prisma Client Python — Async Support

**Decision**: Use `prisma` Python package (Prisma Client Python) in async mode.

- Prisma Client Python supports `asyncio` natively when initialized with `Prisma(auto_register=True)`.
- `schema.prisma` uses `provider = "postgresql"` with `previewFeatures = ["postgresqlExtensions"]` to declare the `pgvector` extension.
- Raw SQL for triggers is delivered via a custom migration SQL file (not generated by Prisma).

**Key config**:
```prisma
generator client {
  provider             = "prisma-client-py"
  interface            = "asyncio"
  recursive_model_name = true
}

datasource db {
  provider   = "postgresql"
  url        = env("DATABASE_URL")
  extensions = [pgvector(map: "vector")]
}
```

**Alternatives Considered**:
- **SQLAlchemy async**: More mature ecosystem but no schema-as-code migration story as clean as Prisma.
- **Tortoise ORM**: Lacks Prisma's type safety and migration tooling.

## R-003: pgvector — Cosine Similarity Query Pattern

**Decision**: Store embeddings as `Unsupported("vector(384)")` in Prisma schema; query via `prisma.query_raw`.

Prisma does not natively support `pgvector` vector type. Pattern:

```python
results = await db.query_raw(
    """
    SELECT p.*, 1 - (pe.embedding <=> $1::vector) AS similarity
    FROM products p
    JOIN product_embeddings pe ON pe.product_id = p.id
    ORDER BY pe.embedding <=> $1::vector
    LIMIT $2
    """,
    query_vector_str,  # e.g., "[0.1, 0.2, ...]"
    limit,
)
```

- `<=>` operator = cosine distance (pgvector). `1 - distance` = cosine similarity.
- An `ivfflat` index with `lists = 100` is created for ANN (approximate nearest neighbor) search at scale.

**Alternatives Considered**:
- **`<#>` (inner product)**: Only correct for unit-normalized vectors; cosine is more robust.
- **`<->` (L2 distance)**: Less suitable for semantic similarity of text embeddings.

## R-004: Embedding Model — sentence-transformers/all-MiniLM-L6-v2

**Decision**: Use `sentence-transformers` library with model `all-MiniLM-L6-v2`.

- Output: 384-dimensional float32 vectors.
- Size: ~80MB model download; cached locally after first run.
- Throughput: ~2000 sentences/sec on CPU; sufficient for v1 worker.
- License: Apache 2.0.

**Source text for embedding**: Concatenation of:
```
{name} {brand} {category} {subCategory} {description} {tags joined by space}
```

Model is loaded once at worker startup and reused across all notifications.

## R-006: asyncpg LISTEN for pg_notify

**Decision**: Use `asyncpg` directly (alongside Prisma) for the LISTEN channel.

Prisma Client Python does not expose raw LISTEN/NOTIFY. A separate `asyncpg` connection is created exclusively for `LISTEN product_embedding_channel`. This connection runs in the FastAPI startup lifespan event.

```python
# embedding_worker.py (simplified)
import asyncpg, asyncio

async def start_worker(dsn: str, model):
    conn = await asyncpg.connect(dsn)
    await conn.add_listener("product_embedding_channel", make_handler(model))
    # Keep alive — runs until app shutdown
```
